# Обновление

## Перед обновлением

1. Прочитайте, что изменилось, в [CHANGELOG.md](../../../CHANGELOG.md): несовместимые изменения и
   новые настройки перечислены там.
2. Сделайте бэкап ([Бэкапы](Backup.md)):

   ```bash
   cd /opt/lamnezia
   docker compose run --rm backup sh /usr/local/bin/backup.sh once
   ```

## Обновление

```bash
cd /opt/lamnezia
git pull
docker compose up -d --build
```

Или запустите установщик ещё раз: он обновит код, а `.env`, сайт nginx и данные оставит как есть.

`git pull` идёт по ветке установки: в `releases` только релизы (её берёт установщик), `dev` —
ветка разработки. Установщик держит код на локальной ветке, которая следит за той же веткой
`origin`, поэтому `git pull` работает и после повторного запуска установщика. Установка на теге
(`LAMNEZIA_REF=vX.Y.Z`) остаётся на этой версии, `git pull` на ней не работает — см. «Релизы».

Установка, сделанная до 1.0, стоит на `main`, которой больше нет, а повторный запуск старого
установщика оставлял код без ветки (`git pull` отвечает «You are not currently on a branch»).
Один раз переведите такую установку на релизы:

```bash
git fetch origin releases
git checkout -B releases origin/releases
```

Миграции базы выполняются сами при каждом запуске `web`. VPN-серверы работают, пока панель
перезапускается; фоновые операции, которые шли в этот момент, через `LAMNEZIA_OPERATION_TIMEOUT`
помечаются прерванными, их можно повторить. Обновлению с 1.0.0 ничего, кроме этих миграций, не
нужно: модератор каждого пользователя становится его единственным сотрудником, а у каждого
модератора остаются его пользователи, серверы, квоты и обращения; доступ администраторов и
модераторов не меняется ([Роли и права](Roles-and-access.md#обновление-с-100)).

Новые необязательные настройки получают значения по умолчанию; сравните свой `.env` с
`.env.example`, чтобы их увидеть ([Настройка](Configuration.md)).

## Обновление из панели

Дважды в день панель спрашивает у GitHub последний релиз (его тег и текст; о самой панели ничего не
отправляется). Когда выходит более новый, администраторы видят его на главной и в **Система →
Обновление панели** со ссылками на релиз и его CHANGELOG. Там же показан текст релиза в разметке
Markdown, HTML из него вырезается; длинный текст свёрнут и раскрывается по щелчку. `LAMNEZIA_UPDATE_CHECK=False` выключает
проверку ([Настройка](Configuration.md)).

На этой странице администратор запускает обновление, указав пароль для архива панели:

1. Панель создаёт архив ([Архив панели](Backup.md#архив-панели)) с этим паролем.
2. Она оставляет запрос в `update/request` каталога установки. У панели нет доступа к Docker и к
   хосту: юнит `lamnezia-update.path` на хосте видит запрос и запускает
   `/usr/local/sbin/lamnezia-deploy release`.
3. Скрипт на хосте принимает только тег релиза `vX.Y.Z` из ветки, за которой следует установка, и
   только новее работающей версии, и сверяет его с манифестом, опубликованным в релизе на GitHub
   (версия, коммит тега и, при `LAMNEZIA_IMAGE`, дайджест образа). У манифеста должна быть верная
   подпись ключом из `deploy/update/release-signers` работающей версии; без неё обновление
   останавливается до каких-либо изменений, а причина видна на странице. Скрипт переводит код на
   тег, пересобирает или скачивает образ, перезапускает панель и ждёт `/healthz`.
4. Если панель не поднялась здоровой, скрипт возвращает предыдущую версию.

Статус и журнал скрипта на хосте показаны на той же странице. Одновременно идёт одно обновление;
запрос, который хост не забрал за час, показывается зависшим. Пока панель
перезапускается, она минуту-две не отвечает.

Миграции базы при откате не отменяются. Если предыдущая версия не работает с обновлённой базой,
восстановите архив, сделанный перед обновлением ([Бэкапы](Backup.md#архив-панели)).

Юнит ставит установщик. Установка, сделанная раньше, показывает новый релиз без кнопки
**Обновить**: один раз запустите `install.sh` текущей версии или обновите панель вручную, как
описано выше. Из панели обновляется только установка из git. Проверить юнит:
`systemctl status lamnezia-update.path`; журнал последнего запуска скрипта — в `update/status/log`.

## Автоматическое обновление из GitHub

Workflow **Deploy** обновляет панель после каждого зелёного CI в `dev` (его можно запустить и
вручную). Он подключается по SSH своим ключом, которому разрешён только скрипт
[`deploy/update/lamnezia-deploy.sh`](../../../deploy/update/lamnezia-deploy.sh): скрипт получает
`dev` (`BRANCH` в его настройках; checkout на сервере должен быть на этой ветке) с временным
токеном задания (на сервере он не сохраняется), переходит на проверенный коммит (запоздавший запуск никогда не откатывает версию), выполняет `docker compose up -d --build` и ждёт
ответа `/healthz`. Если задан `LAMNEZIA_IMAGE` (в `.env` или `/etc/default/lamnezia-deploy`), скрипт
ничего не собирает: вместо этого он выполняет `docker compose pull` и `docker compose up -d --no-build`.
После обновления скрипт удаляет старые образы панели, чтобы они не копили место на диске: после
сборки — образы проекта без тега и кэш сборки старше недели, после `pull` — предыдущую версию образа.
Без секрета `DEPLOY_HOST` workflow ничего не делает.

Настройка, один раз:

1. На сервере установите скрипт и его настройки:

   ```bash
   install -m 755 deploy/update/lamnezia-deploy.sh /usr/local/sbin/lamnezia-deploy
   cat > /etc/default/lamnezia-deploy <<'EOF'
   LAMNEZIA_DIR=/opt/lamnezia
   COMPOSE_PROJECT=lamnezia
   HEALTH_URL=https://panel.example.com/healthz
   EOF
   ```

2. Создайте отдельную пару ключей для обновления (`ssh-keygen -t ed25519 -N "" -f lamnezia-deploy`)
   и добавьте открытый ключ в `~/.ssh/authorized_keys` сервера с ограничением на скрипт:

   ```text
   restrict,command="/usr/local/sbin/lamnezia-deploy" ssh-ed25519 AAAA... lamnezia-deploy
   ```

3. В настройках репозитория (**Secrets and variables → Actions**) добавьте `DEPLOY_HOST`,
   `DEPLOY_SSH_KEY` (закрытый ключ), `DEPLOY_KNOWN_HOSTS` (строка из `ssh-keyscan -t ed25519
   <хост>`), при необходимости `DEPLOY_PORT` (22) и `DEPLOY_USER` (root). После этого удалите закрытый
   ключ со своего компьютера.

Сервер запускает установленную копию скрипта: после изменения `deploy/update/lamnezia-deploy.sh`
установите его заново. Чтобы остановить обновления, удалите строку ключа из `authorized_keys` или
секрет `DEPLOY_HOST`.

## Релизы

Релизы помечаются тегами `vX.Y.Z` ([Semantic Versioning](https://semver.org/lang/ru/)). Чтобы
остаться на определённом релизе, а не на последнем из `releases`:

```bash
git fetch --tags
git checkout vX.Y.Z
docker compose up -d --build
```

С каждым релизом публикуется и готовый образ `ghcr.io/aglamake/lamnezia:X.Y.Z` (и теги `X.Y`, `X`,
`latest`) для `amd64` и `arm64`. Если в `.env` задан `LAMNEZIA_IMAGE`
([готовый образ](Installation.md#готовый-образ-вместо-сборки)), поменяйте в нём версию и выполните
`docker compose pull && docker compose up -d --no-build`.

### Проверка подлинности релиза

Workflow релиза подписывает происхождение образа и файлов релиза (аттестация сборки от GitHub), а
для образа ещё и SBOM — список его пакетов. Кроме `lamnezia-release.txt`, в релизе лежит
`lamnezia-X.Y.Z.tar.gz` — код тега. Проверяет их [GitHub CLI](https://cli.github.com/); успешная
проверка значит, что файл собран workflow релиза этого репозитория:

```bash
gh attestation verify oci://ghcr.io/aglamake/lamnezia:X.Y.Z --repo AGLamake/Lamnezia
gh release download vX.Y.Z --repo AGLamake/Lamnezia
gh attestation verify lamnezia-X.Y.Z.tar.gz --repo AGLamake/Lamnezia
gh attestation verify lamnezia-release.txt --repo AGLamake/Lamnezia
```

SBOM образа проверяется первой командой с добавкой
`--predicate-type https://spdx.dev/Document/v2.3`. У релизов до этого аттестаций нет.

Манифест ещё и подписан SSH-ключом релизов (`lamnezia-release.txt.sig`). Обновление из панели
проверяет эту подпись само; вручную — в каталоге установки (OpenSSH 8.1 или новее):

```bash
ssh-keygen -Y verify -f deploy/update/release-signers -I lamnezia-release -n lamnezia-release \
  -s lamnezia-release.txt.sig < lamnezia-release.txt
```

## Проверка после обновления

- `docker compose ps` показывает `healthy` у `web`, `worker`, `postgres` и `redis`;
- `https://panel.example.com/healthz` отвечает `{"status": "ok"}`;
- в **Операциях** нет новых упавших операций.

## Откат

Миграции автоматически не откатываются. Чтобы вернуться на прошлую версию, восстановите бэкап,
сделанный перед обновлением ([Бэкапы](Backup.md#восстановление-панели)), и переключитесь на прошлый тег.
