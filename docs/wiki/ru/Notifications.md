# Уведомления

**Админка → Уведомления** (`/notifications/`, только администраторы) отправляет события панели на
почту, в Telegram, Discord, в браузеры персонала и в ваши вебхуки.

## Каналы

Канал — одно место, куда приходят сообщения. Каналов каждого вида может быть несколько.

| Вид | Что заполнить |
|---|---|
| Email | Один или несколько адресов через запятую. Письма идут через почтовый сервер панели ([Настройка](Configuration.md)): простой текст и HTML-версия в оформлении панели, ссылка события в ней — кнопкой «Открыть в панели». |
| Telegram | Chat ID пользователя, группы или канала, куда бот может писать. В супергруппе с темами добавьте номер темы через двоеточие, `-1001234567890:42`: это последняя часть ссылки на тему (**Копировать ссылку** → `t.me/c/1234567890/42`); без номера сообщение уходит в General. Токен бота: свой у канала или пусто — тогда берётся из настроек панели. |
| Discord | Webhook URL канала Discord (**Настройки канала → Интеграция → Вебхуки**). Сообщения приходят как embed. |
| Личное сообщение в Discord | ID пользователя Discord (режим разработчика → правый клик → «Копировать ID»). Пишет Discord-бот панели; у пользователя должен быть общий сервер с ботом. |
| Webhook | Ваш URL и секрет подписи. Панель отправляет JSON (см. ниже). |
| Уведомления в браузере | Только название: сообщения идут в браузеры сотрудников, включивших уведомления в профиле, каждому — в пределах его зоны (см. [В браузере](#в-браузере)). |

Токены, адреса вебхуков и секреты хранятся зашифрованно и больше не показываются: оставьте поле
пустым, чтобы сохранить прежнее значение. Выключенный канал не получает ничего, кроме тестового
сообщения.

Адреса вебхуков и Discord должны вести на публичный адрес. Адрес в частной сети (`127.0.0.1`,
`10.0.0.0/8`, `192.168.0.0/16`, `169.254.169.254` и подобные, в том числе за именем хоста)
отклоняется при сохранении канала и проверяется снова при каждой отправке; перенаправления не
выполняются. Отправка соединяется именно с адресом, который прошёл проверку, поэтому имя, сменившее
адрес сразу после проверки (DNS-rebinding), не уведёт запрос в частную сеть. Имя, которое не
разрешается, получит отправку позже, повторной попыткой. Для приёмника в вашей собственной сети включите **Настройки → Интеграции →
Уведомления в частные сети**.

**Отправить тест** сразу отправляет в канал тестовое сообщение; результат — в журнале.

## События и маршруты

На странице канала отметьте события, которые он должен получать. В списке каналов видно, какие
каналы слышат каждое событие.

| Событие | `event` | `data` |
|---|---|---|
| Сервер недоступен | `server_down` | `server`, `host`, `last_seen` |
| Сервер снова отвечает | `server_up` | `server`, `host`, `last_seen` |
| AmneziaWG работает без настроек 3.1 | `awg3_dropped` | `server`, `host`, `since` |
| AmneziaWG снова работает с настройками 3.1 | `awg3_restored` | `server`, `host`, `since` |
| Высокая нагрузка на сервер | `server_load_high` | `server`, `host`, `resource` (`cpu`, `memory`, `disk`), `percent`, `threshold`, `since` |
| Нагрузка на сервер в норме | `server_load_normal` | `server`, `host`, `resource`, `percent`, `threshold`, `since` |
| Пропал VPN-интерфейс | `interface_lost` | `server`, `host`, `container`, `since`, `attempts` |
| VPN-интерфейс восстановлен | `interface_restored` | `server`, `host`, `container`, `since`, `attempts` |
| VPN-интерфейс не восстановлен | `interface_repair_failed` | `server`, `host`, `container`, `since`, `attempts` |
| Ключ подключился | `key_connected` | `user`, `key`, `key_id`, `server`, `url` |
| Достигнут лимит | `limit_reached` | `user`, `reason` (`traffic`, `total_traffic`, `expired`) |
| Доступ скоро закончится | `access_expiring` | `user`, `until` (дата) |
| Трафик скоро закончится | `traffic_low` | `user`, `percent`, `used`, `limit_bytes`, `limit`, `incomplete`, `note`, `url` |
| Ключи нужно импортировать заново | `keys_changed` | `user`, `server` |
| Ключи отозваны | `keys_revoked` | `user`, `server` |
| Ключи переведены на AmneziaWG 3.1 | `keys_moved` | `user`, `server` |
| Ключи обновлены для группы серверов | `keys_updated` | `user`, `server` |
| Ключи переизданы | `keys_reissued` | `user`, `server` |
| Ключи XRay нужно импортировать заново | `short_id_changed` | `user`, `server` |
| Заявка на регистрацию | `registration_pending` | `user`, `email` |
| Вход заблокирован после неверных паролей | `sign_in_locked` | `user`, `address`, `failures`, `minutes` |
| Новое обращение в поддержку | `ticket_created` | `user`, `type`, `subject` |
| Сообщение в чате | `chat_message` | `user`, `text`, `count` |
| Открыт инцидент | `incident_opened` | `server`, `reports` |
| Инцидент закрыт | `incident_closed` | `server` |
| Новое предложение статьи | `suggestion_created` | `user`, `kind`, `title` |
| Оплата получена | `payment_received` | `user`, `plan`, `amount`, `currency`, `provider` |
| Ретранслятор переключился | `relay_switched` | `group`, `relay`, `from`, `to` |
| Сервер группы недоступен с ретранслятора | `member_unreachable` | `group`, `relay`, `server` |
| Ни один сервер группы не доступен | `group_unreachable` | `group`, `relay` |
| Ретранслятор не отвечает | `relay_down` | `relay`, `host`, `last_seen` |
| Сервер группы отстаёт | `member_lagging` | `group`, `server`, `since`, `reason` |
| Сервер группы снова доступен с ретранслятора | `member_reachable` | `group`, `relay`, `server` |
| Сервер группы снова доступен | `group_reachable` | `group`, `relay` |
| Ретранслятор снова отвечает | `relay_up` | `relay`, `host`, `last_seen` |
| Сервер группы догнал группу | `member_caught_up` | `group`, `server`, `since` |
| На ретрансляторе другие настройки | `relay_settings_differ` | `relay`, `host` |
| Настройки ретранслятора снова совпали | `relay_settings_match` | `relay`, `host` |
| Архив панели не создан | `panel_archive_failed` | `error` |
| Домен панели переключился | `panel_domain_switched` | `domain`, `host`, `url` |
| Список сетей не обновлён | `split_list_stale` | `group`, `source`, `days`, `error` |
| Аварийный проброс | `split_emergency` | `group`, `relay`, `server` |
| Снова раздельный режим | `split_restored` | `group`, `relay` |
| Отчёт персоналу | `staff_report` | `period`, `since`, `servers_down`, `relays_down`, `groups_down`, `traffic`, `top_keys`, `access_ending`, `failed_operations`, `backups_oldest`, `archive_at`, `applications`, `new_requests`, `url` |

`server_up` и последние четыре приходят один раз, когда закончился соответствующий сбой
(`server_down`, `member_unreachable`, `group_unreachable`, `relay_down`, `member_lagging`). Панель
помнит сбой отдельно от уведомлений, поэтому пара приходит, даже если на событие сбоя не
подписан ни один канал. Удаление сервера или ретранслятора забывает его сбой без уведомления о
восстановлении; так же забывается отставание сервера, который вышел из группы: догонять ему
больше некого.

**Ключи переизданы** (`keys_reissued`) приходит владельцу один раз на переиздание его ключей на
одном сервере — персоналом, пакетом или после смены настроек группы или протокола: старые ключи
больше не подключаются, новые нужно импортировать заново. Пользователь, который сам переиздал
свой ключ в личном кабинете или боте, уведомления не получает.

`member_unreachable` приходит один раз на сбой участника. Сбой заканчивается и приходит
`member_reachable`, только когда участник 5 минут отвечает на все проверки, которые видела
панель: участник, который отвечает ретранслятору через раз, не повторяет эту пару каждые
несколько минут.

Уведомления о пользователе уходят туда, что он выбрал на странице **Мессенджеры**: по умолчанию
на email или в привязанный Telegram или Discord ([Telegram и Discord](Messengers.md)), а также
в браузеры, где он включил уведомления ([В браузере](#в-браузере)).
Сами пользователи получают письмо о достигнутом лимите, когда израсходована большая часть
лимита трафика (см. ниже), и за три дня до конца доступа, если у них указан адрес. Когда инцидент закрыт, все сообщившие о нём получают письмо, что сервер снова
работает (`incident_resolved`; оно уходит только пользователям, не в каналы).

**Трафик скоро закончится** (`traffic_low`): пользователь с лимитом трафика один раз за период
этого лимита узнаёт, что израсходовал долю, заданную в **Настройки → Пользователи и ключи →
Предупреждение о трафике** (по умолчанию 80%; 0 — выключить). Учитываются лимит тарифа и
личные лимиты пользователя, а также трафик серверов группы. Каждый лимит предупреждает
отдельно: за период и всего. Новый период, другой тариф или изменённый лимит позволяют
предупредить снова; продление того же тарифа период не меняет и повторно не предупреждает.
О достигнутом лимите не предупреждает: о нём приходит `limit_reached`. Если трафик части
ключей пользователя сейчас не считается (сервер не отвечает), в сообщении сказано, что
настоящая доля может быть больше. Сообщение ведёт на страницу расхода в портале и пишется на
языке пользователя.

**Ключ подключился** (`key_connected`): владелец нового ключа один раз узнаёт, что он работает —
при первом замере трафика после выдачи, который видит ключ в деле: рукопожатие или, у протоколов
без него, выросшие счётчики. В группе серверов считается подключение к любому участнику.
Перевыданный ключ того же устройства не сообщает повторно, если ключ этого устройства уже
подключался; импортированные ключи и ключи, выданные до обновления, не сообщают никогда.
Сообщение ведёт на ключ в портале. Администраторам — только если событие направлено в канал
(по умолчанию выключено).

Письмо пользователю, как и в каналы email, — простой текст и HTML-версия в оформлении панели:
заголовок события, текст и ссылка на нужную страницу кнопкой «Открыть в панели». Письмо о конце
доступа и о лимите пользователю без привязанного мессенджера предлагает получать уведомления в
Telegram или Discord (если у панели настроен их бот): в тексте — строкой со ссылкой на профиль, в
HTML — отдельным блоком с кнопкой «Привязать». Письмо пишется на языке получателя.

Ответ поддержки приходит туда, откуда пользователь писал последним: если из бота — сам ответ
уходит в этот мессенджер, даже без email (`chat_answer`, `request_answer`), если с сайта — ждёт
на сайте. Если за 2 минуты пользователь не ответил и не прочитал ответ в панели, туда, что он
выбрал, уходит одно напоминание со ссылкой на переписку, без текста ответа, только
пользователю: «в чате поддержки новое сообщение» для чата (`support_answer`, данные `user`, `url`)
или «на ваше обращение пришёл новый ответ: тема» для обращения (`request_reminder`, данные `user`,
`topic`, `url`). Если сам ответ уже дошёл до этого канала, напоминания нет; ответ, который
мессенджер не принял (бот заблокирован), не считается. Несколько ответов подряд дают одно
напоминание, пока пользователь не напишет. Если выбранный канал недоступен (мессенджер не
привязан, у бота нет токена, бот заблокирован, Discord не принимает личные сообщения, письмо не
ушло), напоминание пробует остальные по очереди — Telegram, Discord, email — кроме канала, куда
дошёл ответ, и останавливается на первом, который его принял; в журнале доставки видны ошибки всех опробованных. Если, кроме
канала, куда дошёл ответ, у пользователя ничего нет, напоминания нет совсем. См.
[Обращения](Support-and-incidents.md).
 Когда обращение ждёт пользователя, решено или закрыто, пользователь узнаёт об этом там, что выбрал (`request_status`; в мессенджер его последнего сообщения в обращении, если оно оттуда). Эти события уходят только пользователю. Так же — решения по предложенной пользователем статье: `suggestion_accepted` (со ссылкой на опубликованную страницу) и `suggestion_rejected` (с причиной), см. [Инструкции](Guides-and-releases.md).

**Уведомления о входе.** О входе из новой сети или браузера узнаёт только владелец учётной
записи (`sign_in_new_place`, данные `user`, `device`, `address`, `url` — сеансы профиля):
администраторы и модераторы всегда, пользователь портала — если включил это в
**Профиль → Уведомления**. Блокировка после неверных паролей уходит в каналы, подписанные на
`sign_in_locked`, один раз за блокировку и без пароля. См. [Безопасность](Security.md#уведомления-о-входе).

**Отчёт персоналу.** В **Настройки → Отчёт персоналу** администратор включает сводку каждый
день или каждую неделю (по умолчанию выключено). Ежедневная уходит в первый час после 9:00 по
времени панели, еженедельная — в понедельник в то же время (или в день, когда её включили).
В ней — какие серверы не отвечают, какие релеи панель не может прочитать и в каких группах
релею не отвечает ни один участник, трафик за период и пять самых активных ключей, клиенты, у
которых доступ заканчивается в течение недели, неудачные операции, время самого старого бэкапа
протокола и последнего архива панели, заявки, ждущие одобрения, и новые обращения в поддержку.
Отчёт собирается из того, что панель уже знает: серверы ни о чём не спрашиваются, и в нём нет
ни одного сайта, который посещал пользователь. Каналы, подписанные на `staff_report`, получают
всю панель. Каждый модератор получает отчёт по своей зоне (`zone_report`, только ему, по почте
или в мессенджер, без релеев, групп, архива и заявок): его серверы, ключи и обращения его
клиентов, запущенные им операции. **Прислать сейчас** под настройкой сразу отправляет отчёт,
чтобы проверить, как он читается (пока отчёты выключены — ежедневный); результат — в журнале
доставки.

Каждое сообщение пишется на языке того, кто его читает. Язык своих уведомлений пользователь
выбирает на странице **Мессенджеры**; пока не выбрал — получает язык сайта (русский). Каналы
всегда получают язык сайта, о ком бы ни было событие. Переключатель RU/EN в шапке панели
меняет и этот язык. `data` вебхука от языка не зависит: слова панели в нём (`type` обращения) —
на английском, а коды (`reason` лимита) остаются кодами; в сообщении они написаны словами:
«трафик за период израсходован», «весь трафик израсходован», «срок доступа закончился».

Сообщения в чате, которые пользователь отправил в течение двух минут, дают одно уведомление.
Оно уходит через две минуты после первого сообщения, каждое сообщение — отдельной строкой
в `text`; `count` в `data` говорит, сколько их.

О сервере, который перестал отвечать, сообщается один раз; повторно — только после того, как он
вернулся и снова пропал. Когда сервер снова отвечает, приходит `server_up`.

Если модуль ядра amneziawg на сервере старше 3.1, amnezia-awg2 работает без настроек AmneziaWG 3.1,
и клиенты с ними не подключаются. Монитор сообщает об этом один раз событием `awg3_dropped` и
подсказывает, что делать: обновить или удалить модуль amneziawg на хосте и перезапустить
amnezia-awg2. Когда настройки вернулись, один раз приходит `awg3_restored`. Если amnezia-awg2
с сервера удалён, сбой забывается без уведомления.

Ещё монитор следит за процессором, памятью и диском каждого сервера по порогам в
**Настройки → Нагрузка на сервер** (по умолчанию 90% у каждого, 0 — не следить). Короткий
всплеск никого не будит: `server_load_high` приходит после нескольких замеров подряд не ниже
порога (по умолчанию 3), а `server_load_normal` — после стольких же замеров ниже него, поэтому
колебания около порога ничего не меняют. Пока нагрузка высокая, `server_load_high` повторяется
не чаще заданного (по умолчанию раз в 6 часов); если нагрузка снова превысила порог раньше,
о ней не сообщается повторно. `server_load_normal` приходит один раз и только если о начале
сообщили. Каждый ресурс отслеживается отдельно. Ретрансляторы не отслеживаются: у них панель
читает только трафик.

Когда контейнер WireGuard-семейства работает, а его интерфейса нет 3 замера подряд (например,
ядро завершило amneziawg-go при нехватке памяти), один раз приходит `interface_lost`, и панель
перезапускает контейнер — не больше 3 раз, с растущей паузой. `interface_restored` приходит один
раз, когда замер снова находит интерфейс; `interface_repair_failed` — один раз, когда
перезапуски не помогли, и панель больше не перезапускает контейнер. `since` — первый замер без
интерфейса, `attempts` — сделанные перезапуски. Остановленный администратором контейнер
завершает наблюдение без уведомления ([Серверы и импорт](Servers-and-import.md#мониторинг)).

## В браузере

Пользователь включает уведомления в **Профиль → Уведомления → В браузере** кнопкой
**Получать уведомления в браузере**: браузер спрашивает разрешение и дальше показывает
уведомления панели, даже когда панель закрыта. Работает в браузерах на компьютере, на Android, а
на iPhone и iPad — с iOS 16.4, если панель добавлена на экран «Домой» и открыта оттуда.
Каждый браузер включается отдельно, до 10 на пользователя; **Отправить тест** проверяет этот
браузер, **Выключить в этом браузере** отключает его. Выход из панели выключает уведомления в
этом браузере, чтобы их не получил следующий, кто им пользуется. Когда браузер сам обновляет
подписку, service worker панели отправляет новую вместо старой, и уведомления идут дальше без
захода в профиль; для этого пользователь должен быть авторизован в панели в этом браузере.

В браузер приходят те же события, что на почту или в мессенджер: конец доступа, лимит, ответ
поддержки и остальное, что адресовано пользователю. Ответ поддержки, уже дошедший до мессенджера
(`chat_answer`, `request_answer`), в браузер не отправляется. Нажатие открывает страницу, о
которой уведомление: расход — для лимита, чат поддержки — для ответа, обращение во входящих — для
нового обращения.

Для персонала есть канал **Уведомления в браузере**: события, направленные в него, приходят в
браузеры активных сотрудников, включивших уведомления в профиле, — например, новое обращение, заявка
на регистрацию или инцидент. Администратор получает все направленные события. Модератор или владелец
— только события своей зоны ([роли и доступ](Roles-and-access.md)): о серверах, которые он ведёт или
которые ему выданы, и о пользователях, которых он обслуживает. Каждое событие относится и к разделу
панели: сотрудник с уровнем **Нет доступа** в этом разделе его не получает — например, модератор
узнаёт о серверах, только когда ему выдан раздел **Серверы**. Событие сервера относится к
**Серверам** (инцидент — к **Входящим**); событие ключей — к **Ключам**; лимиты, трафик, окончание
доступа и входы — к **Пользователям**; заявка на регистрацию — к **Регистрации**; обращение и
сообщение в чате — к **Входящим**; предложение статьи — к **Статьям**; оплата — к **Заказам**.
События о релеях и группах серверов, отчёты и сбой архива панели получают только администраторы.

Панель сама создаёт пару ключей VAPID при первом использовании; закрытый ключ хранится
зашифрованно, как остальные секреты. Отправка идёт только из фонового обработчика через
push-сервис браузера (Google, Mozilla, Apple) и зашифрована для этого браузера (RFC 8291): сервис
не видит текст. Подписка, о которой push-сервис ответил, что её больше нет (HTTP 404 или 410),
удаляется. Адрес push-сервиса проверяется как адрес вебхука: принимается только публичный `https`.

## Доставка и журнал

Сообщения отправляются в фоне. В каждый канал — отдельно: канал с ошибкой не задерживает
остальные. Временная ошибка (нет соединения, таймаут, HTTP 408, 425, 429 или 5xx) повторяется с
растущей паузой 30 секунд, затем 1, 2 и 4 минуты: всего 5 попыток. Остальные ошибки — сразу отказ.

**Журнал** показывает каждую доставку: время, событие, канал, статус, попытки и ошибку. Одно
событие никогда не доставляется в один канал дважды. Доставка, оставшаяся в «Отправляется» после
остановки воркера, через 10 минут отправляется снова или, если попытки кончились, получает отказ.
Отправленные и неудавшиеся доставки удаляются через `LAMNEZIA_NOTIFICATION_RETENTION_DAYS` дней
(по умолчанию 90).
