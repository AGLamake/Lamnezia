# Lamnezia — проектное описание

> Статус: версия 1.0 (2026-11-13). Живой документ: решения меняются здесь, а не в чатах.
>
> **Lamnezia** (Lamake + Amnezia) — self-hosted web panel for Amnezia VPN servers. Работает только с серверами
> и приложением Amnezia. Не является официальным продуктом Amnezia и не связан с её авторами.

## 1. Зачем это нужно

Amnezia VPN (`amnezia-vpn/amnezia-client`) — клиент для ПК и телефонов, который умеет сам поднимать
VPN на VPS по SSH. Для администратора у него есть три боли:

1. **Медленно и хрупко.** Операции с сервером идут долго и иногда падают с ошибками, по которым
   непонятно, что делать.
2. **Нет единой точки управления.** Доступ к серверам приходится заводить отдельно на каждом устройстве.
3. **Нет управления пользователями.** Нельзя увидеть, кто сколько потребил, ограничить трафик,
   срок или число ключей.

**Lamnezia** — self-hosted веб-панель на Django в docker compose, которая разворачивается на VPS под доменом
и становится единой точкой управления: серверы, протоколы, пользователи, лимиты, статистика,
инструкции. Пользователи заходят на тот же сайт и сами получают ключи.

### Для кого

- **Основной сценарий (автор):** VPN для друзей и семьи. Инвайты, лимиты, никакой оплаты.
- **Open-source сценарий:** любой может развернуть у себя. Часть людей захочет **продавать** доступ,
  поэтому в ядре есть тарифы и точки расширения для биллинга, но сам биллинг в ядро не входит до v2.

### Что считается успехом

- Админ больше не открывает приложение Amnezia для повседневных задач.
- Друг получает рабочий ключ за 3 шага без помощи админа.
- Любая ошибка операции на сервере показана человеческим текстом с логом шагов и кнопкой «повторить».
- Чужой человек разворачивает панель по README на чистом VPS за 15 минут.

## 2. Цели, не-цели, анти-цели

**Цели**
- Управление несколькими серверами из одного места.
- Импорт уже существующих серверов Amnezia **без поломки выданных ключей**.
- Установка протоколов с нуля на чистый VPS (основной путь в будущем).
- Пользователи, тарифы, лимиты (трафик, срок, ключи, серверы), автоматическое отключение.
- Сбор и показ статистики трафика: общая и детальная для админа, личная — для пользователя.
- Клиентский портал: самообслуживание по ключам.
- Инструкции со свежими ссылками на релизы Amnezia и FAQ по проблемам.
- Качественный open-source: документация, CI, лицензия, безопасная конфигурация по умолчанию.

**Не-цели (пока)**
- Встроенный приём платежей (только плагины оплаты).
- Свой VPN-клиент или форк приложения Amnezia.
- Агент на сервере (в v1 только агентless через SSH).

**Анти-цели — если это случилось, проект провален, даже если «работает»**
- Панель ломает совместимость с приложением Amnezia на импортированных серверах
  (приложение перестаёт видеть клиентов или перезаписывает изменения панели без следа).
- Выдача или отзыв ключа рвёт соединение остальным пользователям.
- Панель логирует, какие сайты посещают пользователи.
- Утечка базы панели раскрывает SSH-ключи серверов в открытом виде.
- Ошибка вида «Error 300» без объяснения.

## 3. Ограничения и факты о предметной области

Получены изучением `amnezia-client` (коммит от 2026-10-29, релиз 5.0.3.0).

### 3.1 Как Amnezia управляет сервером
- Всё через **SSH + Docker**: `prepare_host.sh` создаёт сеть `amnezia-dns-net` (172.29.172.0/24,
  bridge `amn0`), каждый протокол — отдельный контейнер, собираемый на сервере из Dockerfile
  (`docker build`), конфиги правятся через `docker exec`.
- Имена контейнеров: `amnezia-awg` (legacy AWG), `amnezia-awg2` (AWG 2.0), `amnezia-wireguard`,
  `amnezia-openvpn`, `amnezia-openvpn-cloak`, `amnezia-shadowsocks`, `amnezia-ipsec`, `amnezia-xray`,
  `amnezia-ssxray`; сервисы: `amnezia-torwebsite`, `amnezia-dns`, `amnezia-sftp`, `amnezia-socks5proxy`,
  `amnezia-mtproxy`, `amnezia-telemt`, `amnezia-tproxy`.
- AWG 2.0: конфиг `/opt/amnezia/awg/awg0.conf`, утилита `awg`. Параметры интерфейса:
  `Jc, Jmin, Jmax, S1–S4, H1–H4, HeaderProtectionKey, ContentPaddingAddition, RekeyAfterTime,
  RekeyTimeout, RejectAfterTime, KeepaliveTimeout, MaxHandshakeAttempts, RandomTrailers,
  DisableCookies, I1–I5`. Пустые параметры удаляются из файла. Порт по умолчанию 55424,
  MTU клиента 1376 (десктоп) / 1280 (мобильные). Ключи сервера:
  `wireguard_server_private_key.key`, `wireguard_server_public_key.key`, `wireguard_psk.key`.
- «AmneziaWG 3.1» — тот же контейнер `amnezia-awg2`; версию приложение вычисляет по параметрам в
  `awg0.conf` (3.9).
- Добавление пира: дописать `[Peer]` в конфиг → `awg syncconf awg0 <(awg-quick strip <conf>)`.
  Без рестарта, остальные не отключаются.

### 3.2 Реестр клиентов (ключ к совместимости)
- Файл `/opt/amnezia/<type>/clientsTable` внутри контейнера, где `<type>` — `awg` для **обоих**
  AWG (legacy и 2.0; legacy-конфиг называется `wg0.conf`, 2.0 — `awg0.conf`), `ikev2` для IPsec,
  иначе имя типа в нижнем регистре (`xray`, `openvpn`, …). JSON-массив:
  `[{"clientId": "...", "userData": {"clientName": "...", "creationDate": "...", ...}}]`.
- `clientId` = публичный ключ (WG/AWG), UUID (XRay), имя сертификата (OpenVPN).
- Старый формат — объект `{clientId: {clientName}}`, приложение мигрирует его в массив.
- Приложение при пустой таблице само достраивает её из конфига (`Client N`).
- **Панель обязана читать и писать этот же файл в этом же формате**, добавляя свои данные только
  в дополнительные поля `userData` (например, `lamneziaUserId`), которые приложение игнорирует.

### 3.3 Формат ключа `vpn://`
- `vpn://` + base64url(без `=`) от `qCompress(json, 8)`; `qCompress` = 4 байта big-endian длины
  исходных данных + zlib-поток. Структуру JSON нужно взять 1:1 из `exportController.cpp` и
  проверить импортом в реальное приложение (тест-фикстуры).
- Альтернативы для выдачи: нативный `.conf` для приложения AmneziaWG, QR-код.

### 3.4 Трафик и лимиты
- WG/AWG: `awg show all dump` даёт по пиру `rx/tx bytes` и `latest handshake`.
  **Счётчики обнуляются** при рестарте контейнера и при пересоздании пира → панель хранит
  последние значения и копит дельты; если новое значение меньше прошлого — считается сброс.
- **В протоколах нет встроенных лимитов.** Лимит трафика/срока реализует панель: отключает пира
  (удаляет из живого конфига, но хранит его ключи у себя), при сбросе периода — возвращает.
- XRay: stats API в конфиге Amnezia не включён → панель добавляет в `server.json` блоки
  `stats`/`api`/`policy` и `email` клиента (хеш UUID) при каждом изменении клиентов и читает
  `xray api statsquery` без сброса; перед своим рестартом контейнера снимает показания. Пока API
  не отвечает, источник помечен «статистика недоступна» (`TrafficSource`), а не нулём
  (3.9).
- «Одновременные устройства» можно оценить только приблизительно (по handshake), жёстко — нельзя.

### 3.5 Релизы Amnezia
- `GET https://api.github.com/repos/amnezia-vpn/amnezia-client/releases/latest`.
  Ассеты 5.0.3.0: Windows `.exe`, macOS `.pkg`, Linux `.run`, 8 Android APK
  (`android9-10` / `android11+` × `arm64-v8a`, `armeabi-v7a`, `x86`, `x86_64`). iOS — только App Store.
- Лимит API без токена — 60 запросов/час → кэш в Redis, опциональный `GITHUB_TOKEN`.

### 3.6 Лицензия
- `amnezia-client` — **GPL-3.0**. Если переносим их серверные скрипты/Dockerfile (а для установки
  с нуля это самый надёжный путь), наш проект должен быть GPL-3.0-совместимым.
  **Решено: AGPL-3.0** — совместима с GPL-3.0 и обязывает тех, кто предоставляет сервис на
  модифицированной панели, публиковать изменения. Перенесённые из upstream файлы сохраняют
  указание авторства Amnezia.

### 3.7 Upstream быстро меняется
- AWG 2.0 добавлен недавно, параметры ещё меняются. Весь код знаний о форматах Amnezia
  живёт в одном изолированном пакете (`amnezia_core`, см. 5.2) с фикстурами из upstream,
  чтобы обновление при изменениях upstream было локальным.

### 3.8 Похожие проекты (prior art)
- `kyoresuas/amnezia-api` — REST API поверх контейнеров Amnezia (AWG, AWG2, XRay), без UI.
- `infosave2007/amneziavpnphp` — PHP-панель, SSH, AWG + VLESS, сроки и лимиты.
- `ks-tool/awg-admin`, `Mistgate`, `AmneziaX` — частичные решения (один протокол / свой агент).
- Отличие Lamnezia: Django, совместимость с приложением Amnezia, клиентский портал,
  тарифы, инструкции, качественный open-source.

### 3.9 Проверенные решения: почему так

Выводы исследований, проверенных на upstream `amnezia-client` и на живых серверах.

- **AmneziaWG 3.1.** Это не новый контейнер и не новый формат: тот же `amnezia-awg2`, в `awg0.conf`
  которого есть хотя бы один параметр третьей версии (`HeaderProtectionKey`, таймеры,
  `RandomTrailers`, `DisableCookies`). Версию приложение не хранит, а вычисляет по `awg0.conf`;
  `clientsTable` не меняется. Сервер 2.0 приложение показывает как устаревший и предлагает
  переустановить, а переустановка стирает клиентов панели, поэтому панель сама переводит сервер
  2.0 на 3.1 с сохранением ключей и показывает версию.
- **Учёт трафика XRay.** Других способов считать трафик по пользователям Xray нет: счётчики
  интерфейса общие, IP клиентов ненадёжен. Поэтому (решение автора) панель меняет `server.json`
  сверх списка клиентов: `email` клиента (его UUID, совпадает с `clientId`) и блоки
  `stats`/`api`/`policy`. Ключи, выданные приложением, приходят без `email`; блоки пропадают, если
  администратор поменяет настройки протокола в приложении. Панель возвращает их при следующей
  операции, а до этого показывает «статистика недоступна», а не ноль. Добавление блоков — это
  `docker restart`, то есть переподключение всех клиентов XRay на сервере, поэтому изменения
  копятся и применяются одной записью по протоколу 5.4 (с `xray -test` на новом файле).
- **Скорость XRay.** Лимита скорости на пользователя в Xray нет, а привязаться к IP пира, как в
  AWG, нельзя. Рабочая схема: маршрут по `email` в отдельный outbound `lamnezia-*` с меткой сокета
  и `nftables` в контейнере. Ограничивает в обе стороны и не ломает статистику; пока блоки
  `routing`/outbound пропали, лимиты не действуют.
- **Ссылка-подписка.** Приложение Amnezia не обновляет конфиги своих серверов: конфиг из
  `vpn://`, QR или файла хранится как есть, импорта по http(s)-ссылке нет. Обновляются только
  подписки самой Amnezia через её шлюз, адрес и ключ которого встроены в сборку, — стороннему
  серверу этот механизм недоступен. Поэтому подписка в панели — стандартная ссылка для клиентов
  XRay (v2rayN, v2RayTun, Hiddify, Streisand и подобных). IPv6-адрес в `vless://` берётся в
  скобки, как у upstream (`QUrl::setHost`); в нативном JSON — без скобок.
- **Проверка доступности из браузера.** UDP проверяется через WebRTC: браузер шлёт STUN Binding
  request на `stun:<host>:<port>`, ответ даёт кандидата `srflx`. Порт AWG так не проверить: AWG
  отвечает только на верное рукопожатие. Перенаправлять STUN на порт AWG через iptables
  отказались — это правит правила, которые ведут приложение и Docker. Поэтому на сервер ставится
  отдельный STUN-ответчик (контейнер `lamnezia-probe`, по умолчанию UDP 3478). Цена: проверяется
  доступность хоста по UDP, а не порта AWG — если провайдер режет только AWG или DPI узнаёт его,
  проверка покажет «доступен». Проверка идёт только с устройства пользователя и только для
  серверов, где у него есть ключ; результат в панель не уходит, ответчик ничего не пишет
  (`--log-driver none`).

## 4. Принятые решения

### Автором
- Django + docker compose, деплой на VPS под доменом.
- Две роли интерфейса: админ и клиент. Инструкции с актуальными ссылками на релизы.
- Импорт существующих серверов обязателен; основной путь в будущем — установка с панели.
- Первый протокол — AmneziaWG 2.0.
- Ядро для «друзей», но с расчётом на монетизацию у других.
- Лицензия AGPL-3.0 и название Lamnezia; проект только для Amnezia.
- Приватные ключи клиентов хранятся в панели; админ переключателем решает, может ли пользователь
  смотреть ключ повторно или только при первом открытии (6.5).
- Режим регистрации выбирает админ: по инвайту / открытая с автоназначением / открытая с ручным
  распределением (6.6).

### Технические решения (можно пересмотреть)
| Решение | Почему |
|---|---|
| Python 3.12, Django 5.2 LTS | LTS до 2028 |
| PostgreSQL 16, Redis 7 | стандарт, Redis — брокер Celery и кэш |
| Celery + Celery Beat | все SSH-операции и сбор статистики — фоновые задачи |
| Caddy 2 как reverse proxy | автоматический HTTPS Let's Encrypt без настройки |
| ASGI: gunicorn с uvicorn-воркерами + Django Channels (channel layer в Redis) | WebSocket для чата поддержки; обычные страницы работают как прежде |
| Django templates + HTMX + Alpine.js (CSP-сборка) + Tailwind 4 (standalone CLI, без Node) | без SPA, меньше кода и зависимостей, легко контрибьютить; подробнее — «Интерфейс» ниже |
| paramiko для SSH | зрелый, работает в Celery-воркерах синхронно |
| `cryptography`: X25519 для ключей, Fernet для шифрования секретов | одна библиотека |
| `segno` для QR, `django-otp` для 2FA, `django-axes` для защиты логина | малые зависимости |
| Графики — SVG, который рисует сервер (теги `{% sparkline %}`, `{% bar_chart %}`) | без JS-библиотек и сборки, работает при строгом CSP |
| aiogram 3 (Telegram), discord.py (Discord) | зрелые async-библиотеки; ядро команд от них не зависит |
| uv + pyproject.toml, ruff, pytest-django | быстрый стек разработки |
| Внутренние документы на русском; README — EN + RU | автор русскоязычный, проект публичный |
| Агентless (только SSH) в v1 | ничего не ставим на сервер сверх того, что ставит Amnezia |
| Приватные ключи клиентов шифруются в БД (Fernet), хотя автор допускал открытый вид | для админа и пользователя ничего не меняется, но утёкший дамп/бэкап БД не раскрывает ключи всех пользователей |
| Тариф (Plan) одновременно служит «группой»: в нём серверы и лимиты | одна сущность вместо двух; отдельные группы — если понадобятся |
| Имена в коде: пакет `lamnezia`, env-префикс `LAMNEZIA_`, лок `/opt/amnezia/.lamnezia.lock` | новое название проекта |

### Интерфейс

Стек остаётся серверным: Django-шаблоны отдают готовый HTML, HTMX подменяет фрагменты, Alpine
держит мелкое состояние на странице (меню, раскрывашки), Tailwind 4 собирает CSS из токенов.
SPA с отдельным API рассматривали и отклонили: второй слой логики, сборка на Node, дублирование
прав доступа и валидации — при том, что панели нужны формы, таблицы и прогресс операций, а не
офлайн-клиент.

- **Токены** — CSS-переменные `--ln-*` в `assets/css/app.css`: цвета поверхностей, текста,
  акцента, статусов, тени, радиусы. Тёмная тема переопределяет те же переменные; выбор «светлая /
  тёмная / системная» хранится в `localStorage` и применяется `static/js/theme.js` до отрисовки.
- **Компоненты** — классы в `@layer components` того же файла (`btn`, `field`, `table-cards`,
  `dialog`, `toast`, `badge`, `empty`, `skeleton`, `stat`) и шаблоны `templates/components/`.
  Витрина всех компонентов — `/dev/ui/` (только при `DEBUG`).
- **Каркасы** — `templates/layouts/`: админка (боковое меню, на телефоне выезжает слева), портал
  (меню сверху, на телефоне — нижняя панель вкладок), вход. Хлебные крошки — блок `breadcrumbs`.
- **Без `'unsafe-eval'` и инлайн-скриптов.** Alpine — CSP-сборка: в атрибутах только простые
  выражения, логика — в `Alpine.data` и делегированных обработчиках `static/js/ui.js`
  (`data-confirm`, `data-toast`, `data-dialog-open` и др.). Тест `config/tests/test_csp.py`
  проверяет шаблоны.
- **Доступность — WCAG 2.2 AA**: контраст токенов, видимый фокус, цели нажатия ≥ 24 px,
  `aria-*` у полей с ошибками, диалоги на `<dialog>`. Проверяется axe-core на витрине в обеих
  темах на 360 px и 1280 px.
- **Динамика по дням** — SVG-спарклайны (`{% sparkline %}`), а не таблицы; таблица остаётся
  под раскрывашкой для точных чисел.
- **Страницы ошибок** 400/403/404/500 и отказ CSRF — в дизайне панели, RU/EN; 500-я не трогает
  БД и контекст запроса.

## 5. Архитектура

Подробные схемы — [ARCHITECTURE.md](ARCHITECTURE.md).

### 5.1 Сервисы docker compose
`caddy` (80/443, HTTP + WebSocket) → `web` (ASGI: Django + Channels) ↔ `postgres`, `redis`; `worker` (Celery, SSH-операции, доставка уведомлений),
`beat` (расписание: сбор трафика, health, применение лимитов, сверка), `bots` (опционально, профиль
`bots`: Telegram и Discord). Всё состояние — в томах
`postgres-data`, `caddy-data`, `media`.

### 5.2 Структура кода (Django-приложения)
| Пакет | Ответственность |
|---|---|
| `amnezia_core/` | **Чистый Python без Django**: парсинг/сериализация `awg0.conf`, `clientsTable`, генерация ключей, распределение IP, `vpn://`, разбор `awg show dump`. 100% unit-тесты на фикстурах |

### 5.3 Ключевые сущности
- **Server**: имя, хост, порт, SSH-пользователь, зашифрованный ключ/пароль, страна/метка, статус,
  метрики хоста, дата оплаты VPS (опц.).
- **ProtocolInstance**: сервер, тип контейнера, порт, параметры (JSON), ключи сервера (зашифр.),
  подсеть, источник (`imported` / `installed`).
- **AccessKey**: пользователь (nullable для «ничьих» импортированных), ProtocolInstance, имя устройства,
  `clientId` (pubkey), приватный ключ клиента (зашифр., только для выданных панелью), IP,
  статус (`active` / `disabled_limit` / `disabled_manual` / `revoked`), даты.
  Импортированные ключи **не имеют приватного ключа** → их нельзя переотправить, только отозвать или «привязать» к пользователю.
- **Plan**: лимит трафика за период + длина периода, общий лимит, макс. ключей, срок доступа (дни),
  разрешённые серверы/протоколы, пробный флаг, поля `price`/`currency` (не используются ядром).
- **UserLimits**: переопределения плана на пользователя, дата окончания доступа.
- **TrafficCounter** (последние сырые значения по ключу) и **TrafficHourly** (агрегаты).
- **Operation** / **OperationStep**; **AuditEvent**; **Invite**; **Release** (кэш).
- **SiteSettings** (одна запись, правится в админке): режим регистрации, тариф по умолчанию,
  подтверждение email, политика повторного показа ключей, SMTP, Telegram, GitHub-токен, брендинг.
- **User.status**: `active` / `pending` (ждёт распределения админом) / `blocked`.
- **AccessKey.first_viewed_at** — когда пользователь впервые открыл ключ (для политики 6.5).

### 5.4 Протокол безопасной записи на сервер (обязателен для всех мутаций)
1. Взять серверную блокировку: `flock /opt/amnezia/.lamnezia.lock` (перекрывает и параллельные
   задачи панели).
2. **Перечитать** `awg0.conf` и `clientsTable` с сервера (не доверять кэшу — приложение могло изменить).
3. Применить изменение к прочитанному состоянию через `amnezia_core`.
4. Записать во временный файл → атомарный `mv`; затем `awg syncconf`.
5. Обновить `clientsTable` тем же способом.
6. Снять блокировку, записать шаги в `Operation`, событие в `AuditEvent`.
Приложение Amnezia блокировку не знает → риск гонки остаётся, минимизирован перечитыванием;
задокументировать «не правьте один сервер одновременно в приложении и панели».

### 5.5 Сбор трафика и лимиты
- Beat каждые 5 минут (настраивается): `awg show all dump` по каждому AWG-инстансу → дельты →
  `TrafficHourly`. Обнаружение сброса счётчика.
- Каждые 5 минут — применение лимитов: превышение трафика/срока → отключение пира
  (операция по 5.4) + уведомление. Начало нового периода/продление → включение.
- Онлайн = handshake < 3 минут; у XRay (без handshake) — рост счётчиков в чтении за интервал + 3 минуты.

## 6. Функциональность по разделам

### 6.1 Админ
- Дашборд: серверы (онлайн, CPU/RAM/диск, трафик, активные пользователи, дни до оплаты VPS).
- Серверы: добавить (SSH ключ/пароль), проверить, импортировать существующий, установить протокол,
  перезапустить/удалить контейнер, логи контейнера, правка параметров протокола с предупреждением
  «изменение параметров обфускации требует перевыпуска всех ключей».
- Пользователи: список, фильтры, тарифы, переопределения, массовые действия (продлить, отключить,
  сменить тариф, перенести на другой сервер).
- Ключи: все ключи, «ничьи» импортированные (привязать/отозвать), сверка с сервером (drift).
- Статистика: по серверу/пользователю/ключу/периоду, топ потребителей, онлайн сейчас, неактивные
  ключи, прогноз исчерпания, CSV, `/metrics` (Prometheus, опц.).
- Журнал действий, журнал операций с повтором.
- Поддержка: входящие чаты, обращения и инциденты (6.7).
- Инвайты с предустановленным тарифом; очередь новых пользователей в режиме `open_manual`.
- Настройки (SiteSettings): режим регистрации и тариф по умолчанию, политика показа ключей, SMTP,
  Telegram-бот, GitHub-токен, тексты FAQ, брендинг (название, логотип).

### 6.2 Клиент
- Регистрация по режиму из 6.6; вход — пароль или magic-link на email.
- «Получить ключ»: сервер → устройство (авто-определение по User-Agent) → ссылка на нужную сборку
  приложения + `vpn://` + QR + `.conf`.
- Мои ключи: переименовать, перевыпустить (старый отзывается сразу), удалить.
- Использование: полоса «34 из 100 ГБ», дата сброса, срок доступа, предупреждения.
- Статус серверов, инструкции, FAQ.

### 6.3 Инструкции
- Страница на платформу (Windows, macOS, Linux, Android, iOS) со свежей ссылкой из GitHub-релиза,
  выбор APK (Android 9–10 / 11+, архитектура; по умолчанию arm64-v8a для 11+).
- FAQ «не подключается», «медленно», «нет интернета после подключения», «ключ не импортируется»
  и т. д. — редактируется админом (Markdown).

### 6.4 Ограничения (полный список)
Трафик за период со сбросом; общий трафик; число ключей; срок доступа; разрешённые серверы и
протоколы; пробный период. v2: скорость (`tc`), приблизительный лимит одновременных устройств.

### 6.5 Повторный показ ключей
- Настройка `key_reveal_policy` в SiteSettings:
  - `always` — пользователь видит `vpn://`, QR и `.conf` в любой момент;
  - `once` — полный ключ показывается только при первом открытии (`first_viewed_at`), дальше
    только имя и статус. Потерял — перевыпуск (старый ключ отзывается).
- По умолчанию: `always` — для сценария «друзья» удобнее.
- Админ всегда может посмотреть ключ (действие пишется в журнал) и сбросить `first_viewed_at`.
- Импортированные ключи без приватной части нельзя показать никому — только перевыпуск.

### 6.6 Режимы регистрации
- `invite_only` (по умолчанию) — регистрация только по инвайт-ссылке; тариф берётся из инвайта.
- `open_auto` — открытая регистрация, новому пользователю сразу назначается тариф по умолчанию
  (а с ним серверы и лимиты).
- `open_manual` — открытая регистрация, пользователь получает `status=pending`: видит инструкции и
  сообщение «ожидайте подтверждения», ключей не получает; админ видит очередь новых и назначает тариф.
- Инвайты работают в любом режиме и имеют приоритет (тариф из инвайта, без очереди).
- Подтверждение email (вкл. по умолчанию, если настроена почта) — при любой регистрации, и по
  инвайту тоже: инвайт говорит, кому можно войти, а не что адрес его. Для открытых режимов ещё
  ограничение частоты регистраций по IP и уведомление админу о новых заявках.

### 6.7 Поддержка: обращения и чат
**Единая модель.** `Conversation` — тред сообщений между пользователем и админами. Вид:
`chat` (один общий чат на пользователя) или `ticket` (обращение). У обращения есть тип
(`bug`, `server_down`, `question`, `other`), статус (`new` → `in_progress` → `waiting_user` →
`resolved` → `closed`), приоритет и исполнитель (админ/модератор). `Message` — текст + вложения
(изображения до 5 МБ), автор, время, прочитано. Чат и обращения используют один механизм сообщений.

**Пользователь**
- Кнопка «Сообщить о проблеме» → форма: тип, описание, скриншот. К обращению автоматически
  прикладывается контекст: тариф, ключи, последний handshake по ключам, версия браузера/ОС.
- **Быстрая форма «Сервер не работает»** — в один клик со страницы статуса или ключа: выбор
  сервера (подставлен), необязательный комментарий. Панель сразу запускает проверку сервера и
  прикладывает результат (доступен ли SSH, работает ли контейнер, когда последний раз был трафик).
- Чат с админом в реальном времени (WebSocket), история, индикатор непрочитанного; при обрыве
  WebSocket — опрос раз в 15 с.
- Уведомление об ответе админа, если пользователь не на сайте (email/Telegram, если привязан).
- Ограничение частоты (например, 5 обращений в час), чтобы не заспамили.

**Админ — входящие**
- **Чаты:** список с непрочитанными сверху, фильтры и сортировка по тарифу (группе), серверу,
  статусу пользователя, последнему сообщению; поиск по пользователю и тексту.
- **Обращения:** список с фильтрами по типу, статусу, серверу, тарифу, исполнителю, дате;
  назначение исполнителя, смена статуса, внутренние заметки (не видны пользователю).
- **Инциденты:** обращения `server_down` по одному серверу в течение 30 минут группируются в
  инцидент со счётчиком «сообщили N человек»; закрытие инцидента закрывает все его обращения и
  уведомляет пользователей; при открытом инциденте статус сервера на странице статуса меняется.
- Шаблоны быстрых ответов.

**Маршрутизация уведомлений** (общая для всей панели, не только поддержки)
- Каналы настраиваются отдельно: **email** (SMTP), **Telegram** (токен бота + chat_id, можно несколько),
  **Discord** (webhook-URL канала, сообщения в виде embed; личные сообщения — через бота из 6.8),
  **webhook** (URL, HMAC-SHA256 подпись тела секретом в заголовке `X-Lamnezia-Signature`, ретраи с
  backoff, журнал доставки). Можно завести несколько каналов каждого типа.
- Правила: событие → набор каналов. События: новое сообщение в чате, новое обращение (по типу),
  инцидент открыт/закрыт, сервер упал (мониторинг), превышение лимита, новая заявка на регистрацию.
- Кнопка «отправить тестовое» у каждого канала. Тело webhook — стабильный JSON со схемой в документации.
- Ответ пользователю прямо из бота (reply на уведомление) — см. 6.8.

### 6.8 Боты Telegram и Discord, привязка аккаунтов
**Привязка** (в профиле портала, можно обе):
- Telegram: кнопка «Привязать» → deep-link `t.me/<bot>?start=<одноразовый токен>` (живёт 10 мин,
  одноразовый, хранится хэш) → бот связывает `telegram_id` с пользователем.
- Discord: OAuth2 (scope `identify`) → `discord_id`; запасной путь — одноразовый код командой `/link`.
- Отвязка в профиле и командой в боте. Один мессенджер-аккаунт — один пользователь панели.
- Опционально (настройка админа): вход на сайт через привязанный Telegram (Login Widget) / Discord OAuth2.
- Пользователь выбирает, куда получать свои уведомления: email, Telegram, Discord (6.7).

**Пользовательские команды** (одинаковые в обоих ботах; в Discord — slash-команды в личке,
ответы с ключами — только в ЛС или ephemeral):
- статус: трафик «34 из 100 ГБ», дата сброса, срок доступа;
- мои ключи; новый ключ (сервер → устройство → `vpn://` + QR картинкой + `.conf` файлом
  + ссылка на приложение под устройство); перевыпуск; удаление;
- статус серверов; «сервер не работает» (та же быстрая форма, что в 6.7);
- поддержка: сообщения боту попадают в чат пользователя с админами, ответы админа приходят в бот;
- инструкции и FAQ ссылками на сайт.
- Pending-пользователь (6.6) видит только статус заявки и инструкции.

**Админские команды** (только для пользователей с ролью admin/moderator): сводка по серверам,
трафик за сегодня, открытые инциденты с кнопками «взял» / «закрыть», ответ пользователю
reply-ем на уведомление об обращении.

**Безопасность и настройки**
- Политика показа ключей (6.5) действует и в ботах.
- Настройка `bot_key_delivery`: `allowed` (по умолчанию — для сценария «друзья») или `link_only`
  (бот присылает только ссылку на портал). Причина: переписка в Telegram и Discord не шифруется
  end-to-end и хранится у платформ.
- Rate limit команд; бот никогда не показывает данные без привязки; все действия — в журнал.

**Техника**
- `apps/bots`: платформонезависимое ядро команд и диалогов (кнопки, шаги, i18n) поверх тех же
  сервисов, что и веб (выдача ключей, лимиты, поддержка), и адаптеры: Telegram (aiogram 3;
  webhook через Caddy или long polling) и Discord (discord.py; gateway).
- Отдельный сервис compose `bots` в профиле `bots` (не запускается, пока не заданы токены).

## 7. Нефункциональные требования
- **Безопасность:** секреты (SSH-ключи, приватные ключи клиентов) — Fernet с ключом из env
  (`LAMNEZIA_ENCRYPTION_KEY`), не хранятся в образе; 2FA обязательна для админов (настраиваемо);
  `django-axes`; secure cookies, HSTS, CSP; панель не логирует посещённые сайты; SECURITY.md.
- **Надёжность:** каждая SSH-операция идемпотентна или безопасно повторяема; таймауты; ретраи.
- **Ошибки:** каталог известных ошибок → человеческое сообщение + «что сделать».
- **Производительность:** до 50 серверов и 2000 ключей на одном VPS 2 vCPU / 2 GB.
- **i18n:** RU и EN с первой версии интерфейса.
- **Тесты:** `amnezia_core` — unit на фикстурах из upstream; SSH — интеграционные против
  docker-контейнера с sshd + AWG (в CI — по возможности); Django — pytest-django.
- **Качество кода:** чистый, лаконичный ООП-код для поддержки людьми — обязательный стандарт [CODE_STYLE.md](CODE_STYLE.md).
- **Документация:** wiki (RU/EN) в `docs/wiki/` с публикацией в GitHub Wiki и полный README (RU/EN).
- **Обновления:** `docker compose pull && docker compose up -d`, миграции применяются автоматически.
